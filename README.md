# CampusOS

CampusOS is a React school operations workspace with role-specific dashboards, a Three.js / React Three Fiber campus landing experience, and an Express API. PostgreSQL persists deployed records; a local JSON database supports development demos.

## Run locally

Use Node.js 24 LTS and npm.

```sh
npm run setup
cp .env.example server/.env
npm run dev
```

Open http://localhost:5173. The API runs on http://localhost:4000 and the Vite development server proxies `/api` and `/ws`. `VITE_API_BASE` is optional and public; never use it for secrets. Production uses same-origin `/api` requests.

Local demo staff access:

- Portal: http://localhost:5173/staff/login
- Username: `staff.operations`
- Password: `StaffDemo!2026`

These credentials only apply to the development demo database. Demo seeding and legacy demo passwords are blocked in production. Set `CAMPUSOS_DEMO_STAFF_PASSWORD` before creating a fresh demo database to choose a private development password. Do not deploy local data or use demo credentials for a client institution.

Other local roles are generated by `server/src/seed.ts`. Pending and disabled accounts cannot sign in. Access requests require administrator approval; administrator accounts are provisioned by an authorized operator.

## Verification

```sh
npm test             # API client unit tests and isolated backend integration tests
npm run build        # Typecheck and build client and server
npm run audit        # Audit root, client and server dependency trees
npm run test:roles   # Isolated HTTP system tests across all six roles
npm run test:system  # Read-only HTTP smoke checks against an already running API
```

For system tests, provide `CAMPUSOS_TEST_IDENTIFIER`, `CAMPUSOS_TEST_PASSWORD` and optionally `CAMPUSOS_TEST_ROLE` (defaults to `STAFF`) through your terminal or secret manager. `SYSTEM_API_BASE` defaults to `http://localhost:4000/api`. The test signs in, reads account/operational data and checks access restrictions. Sign-in creates audit entries; it does not change academic records.

Backend tests use temporary, isolated data. They cover login/account status, input validation, role/record ownership, leave persistence/approval, notification privacy, report calculations, password changes/session revocation, and database transaction behavior. Client tests cover request construction, session invalidation, storage restrictions, malformed/network responses and token rotation. `.github/workflows/ci.yml` runs these checks on pushes to main and pull requests.

These checks do not replace client acceptance, a load test, backup restoration rehearsal or an independent security review. See [the test and release notes](docs/QUALITY_AND_RELEASE.md) for recorded results and known deployment limits.

## Production configuration

The existing Vercel project builds `client/dist` and serves API requests through `api/[...path].ts`. Keep the API rewrite in `vercel.json` aligned with the catch-all handler. Node.js 24 is the project runtime.

Configure server-only environment variables separately for each deployment environment:

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection string; required in production and on Vercel. |
| `JWT_SECRET` | Random signing secret of at least 32 characters; use independent preview and production values. |
| `ALLOWED_ORIGINS` | Comma-separated permitted origins when cross-origin API access is needed. |
| `SCHOOL_TIMEZONE` | School calendar timezone; defaults to `Asia/Kolkata`. |

Use separate staging and production databases. The current existing Vercel integration assigns `DATABASE_URL` to development, preview and production; verify isolation before performing staging writes. Never log credentials, commit `.env` files or include local data in deployment artifacts.

Deployed data is stored as a versioned application state document in `campusos_state` on PostgreSQL. API requests acquire a database lock and commit writes before returning success. This preserves the existing application's data adapter; it is not a normalized relational schema. Measure concurrency and payload growth before expanding to a larger institution.

### Provision real accounts

An authorized operator can run:

```sh
NODE_ENV=production npm --prefix server run provision:user
```

The command reads one JSON object from hidden stdin containing `email`, `password`, `fullName`, `role` and `databaseUrl`. Use a password of 12 to 128 characters and a real institutional account address. It creates one approved account and refuses to overwrite an existing user. It does not create an institution's student/faculty profile or class links; administrators must set up the corresponding records.

`CAMPUSOS_USER_EMAIL`, `CAMPUSOS_USER_PASSWORD`, `CAMPUSOS_USER_NAME`, `CAMPUSOS_USER_ROLE` and `DATABASE_URL` may alternatively be supplied as environment variables. Do not put credentials in shell command arguments or repository files. Remove provisioning-only credentials after use. Verify login using the portal corresponding to the created role.

Changing a password in Settings requires the current password, rotates the current token and invalidates older sessions. Password recovery currently records a recovery request for administrators; it does not send email. The interface states this limitation.

### Release and operation

Run tests/build/audit, deploy a preview against staging data, verify each role in the browser, then release the reviewed commit through the existing Vercel project. Verify API health, login, ownership restrictions and key write/read flows against the intended environment. Configure provider backups and operational monitoring, rehearse restoring a backup, and retain a tested previous deployment for rollback. Never treat a successful frontend build as evidence that production database access works.

### Staff teams

Staff members can use **Staff teams** (`/staff-services`) or the dashboard shortcut to find technicians, IT support, laboratory support, maintenance, housekeeping, security, transport, office, library, healthcare and other staff. Categories, search and work contacts use actual personnel records. Salary, bank, PAN and payroll fields are excluded from this directory. Students and parents cannot access it.

Administrators manage staff categories and records in **Staff & HR**. Archiving preserves the HR record and removes it from the active team directory; changing the status back to ACTIVE restores it. A personnel record and a workspace sign-in account are distinct: use **Users & Access** for account approval. Development seed data includes clearly identified demo support-team records; production never inserts these demos.
